# Реестр сущностей

Цель: добавить новый тип клетки, врага, экипировки или босса так, чтобы ядро (`core/`) и игровой цикл не менялись. Новая сущность = запись в реестре + строки в CSV + тесты.

Источник требований: `GDD.md`, §3.4 (клетки), §3.5 (враги), §7 (экипировка), §12.5 (боссы), §19 (бэклог).

---

## 1. Принцип

1. **Данные отделены от поведения.** Параметры (HP, урон, шансы, длительности) — в `balance/balance.csv`. Поведение — функции-обработчики в реестре.
2. **Ядро не знает конкретных типов.** `core/run` вызывает обработчики через реестр: `registry.cells[type].on_enter(...)`, а не `if type == "HEAL"`.
3. **Новая сущность не требует правок ядра.** Если для добавления нужно менять `core/run.lua`, значит не хватает точки расширения. Тогда сначала добавляем точку расширения, отдельным коммитом.
4. **Ключи стабильны.** Ключ (`TYPE_1`, `HEAL`, `CROSSBOW`) не меняется после появления в сохранениях. Отображаемое имя — поле `label`.

---

## 2. Структура реестров

```
core/registry/
├── init.lua          собирает все реестры, проверяет уникальность ключей
├── cells.lua         типы клеток
├── enemies.lua       типы врагов
├── equipment.lua     предметы экипировки
├── bosses.lua        боссы
└── row_kinds.lua     типы рядов (обычный, босс, чекпоинт, лагерь)
```

Каждый реестр — таблица `ключ → запись`. Запись:

```lua
-- core/registry/cells.lua (пример, не финальный)
local balance = require("core.data.balance")

local M = {}

M.HEAL = {
    label = "HEALTH",
    amount = balance.cells.HEAL.amount,
    -- обработчики (все опциональны)
    on_enter = function(ctx, cell)      -- игрок наступил
        ctx:heal(cell.amount)
        return { { type = "heal", amount = cell.amount } }   -- события для скрипта
    end,
}

return M
```

Обработчики получают контекст (`ctx`) — узкий интерфейс над состоянием мира, а не доступ ко всему. Возвращают список событий (см. `docs/ARCHITECTURE.md` §5).

## 3. Что описывает запись каждого реестра

### 3.1 Клетка (`cells`)

| Поле | Обязательное | Назначение |
|---|---|---|
| `label` | да | имя для UI |
| `blocks_movement` | нет (по умолчанию `false`) | стена и подобные |
| `blocks_vision` | нет | стена |
| `on_enter(ctx, cell)` | нет | наступление игрока |
| `on_leave(ctx, cell)` | нет | уход с клетки |
| `on_turn(ctx, cell)` | нет | тик хода (для таймеров, ловушек) |
| `visibility` | нет | `"visible"` (по умолчанию) или `"hidden"` (открыто: скрытые ловушки, §19 бэклога) |
| параметры | по необходимости | из CSV: `amount`, `value`, `damage` |

Текущие клетки: EMPTY, WALL, HEAL, GOLD, ENEMY, ATTACK_CELL, CAMP. Клетки AMMO удалены (GDD §3.4).

Будущие (бэклог): ловушка, ключ, сундук, клетка NPC.

### 3.2 Враг (`enemies`)

| Поле | Обязательное | Назначение |
|---|---|---|
| `label` | да | имя |
| `base_hp` | да | база для окна силы |
| `vision_range` | да | обзор по своему ряду |
| `vision_shape` | нет | `"row"` (по умолчанию) или `"sides"` (WARDEN) |
| `weight` | да | вес спавна |
| `gold_drop` | нет | золото при смерти (CSV) |
| `on_attacked_from_behind(ctx, enemy)` | нет | поведение «в спину» по умолчанию общее |

Урон врага всегда = текущему HP (GDD §3.5). Поле `damage` не вводится: это правило ядра, не данные типа.

### 3.3 Экипировка (`equipment`)

| Поле | Обязательное | Назначение |
|---|---|---|
| `label` | да | имя |
| `slot` | да | слот (`weapon` и т.д., число слотов открыто, GDD §20.1) |
| `max_charges` | да | максимум зарядов (CSV) |
| `damage` | если атакует | урон |
| `range` | если атакует | дальность |
| `recharge_turns` | да | ходов на полное восстановление после исчерпания (CSV) |
| `use(ctx, target)` | да | применение; возвращает события |

Общий принцип (GDD §7) реализуется в ядре один раз: расход заряда, исчерпание, таймер восстановления. Предмет указывает только свои числа и `use`. Новый предмет с зарядами не требует своей логики перезарядки.

### 3.4 Босс (`bosses`)

| Поле | Обязательное | Назначение |
|---|---|---|
| `label` | да | имя |
| `hp_multiplier` | да | множитель от `player.hp` (CSV, по номеру босса) |
| `ai` | да | функция выбора хода `ai(ctx, arena) -> action` |
| `arena_layout` | нет | правила наполнения арены (переопределение базового) |
| `on_defeated(ctx)` | нет | эффекты после победы (лут — бэклог) |

Базовый шаблон AI (профили DR, GDD §12.5) вынесен в `core/ai/boss_default.lua`. Новый босс — собственный `ai` или обёртка над базовым.

Босс выбирается по номеру: `bosses` задаёт порядок или правило выбора. Правило — в `core/boss_schedule.lua`: каждые K рядов, K из CSV.

### 3.5 Тип ряда (`row_kinds`)

Ряд имеет тип: `normal`, `boss`, `checkpoint`, `camp`. Тип определяет генерацию (§13 GDD) и допустимое поведение. Новый тип ряда (например, событийный) — запись здесь.

## 4. Пошаговое добавление сущности

Пример: добавляем клетку «ЛОВУШКА» (бэклог, пример процедуры).

1. **Решение.** Записать в GDD: поведение, видимость, параметры. Без записи в GDD сущность не добавляется.
2. **CSV.** Добавить параметры в `balance/balance.csv`: `cells.TRAP.damage,4,...`, при необходимости шанс в таблице генерации.
3. **Сборка баланса.** `python tools/build_balance.py`.
4. **Реестр.** Добавить запись в `core/registry/cells.lua`. Только данные и обработчики этого типа.
5. **Генерация.** Если клетка появляется при генерации, добавить её шанс в таблицу. Ядро генерации читает таблицу, а не перечисляет типы.
6. **Тесты.** Новый файл `tests/cells/trap_test.lua`: обработчик, границы, влияние на видимость. Тест реестра проверяет, что все поля обязательные присутствуют.
7. **Проверка.** `lua tests/run.lua`, `python tools/build_balance.py --check`, загрузка в редакторе без ошибок.

Ядро не менялось. Если шаг 4–6 требует правки `core/run.lua`, это сигнал: нужна точка расширения. Её добавляем отдельно.

## 5. Проверки реестра (обязательны, в `tests/registry_test.lua`)

- Ключи уникальны в каждом реестре.
- Все обязательные поля присутствуют.
- Все ссылки на CSV-параметры существуют (`balance` геттер бросает ошибку на отсутствующий ключ).
- Все `weight` и шансы неотрицательны; сумма шансов на клетку ≤ 1 для всех номеров рядов, которые проверяются.
- Каждая сущность из реестра упомянута в GDD (проверка по списку ключей в `docs/ENTITY_REGISTRY.md` не автоматическая; поддерживается вручную при ревью).

---

## 6. Правила для ИИ-агента

- Новая сущность добавляется через реестр, не через `if/elseif` в ядре.
- Параметры — только из CSV, никаких литералов в обработчиках.
- Обработчик не меняет глобальное состояние напрямую: только через `ctx` и возврат событий.
- Ключ сущности не переименовывать: это ломает сохранения. Для переименования — миграция `save_schema`.
- Сущность без записи в GDD не добавлять.
